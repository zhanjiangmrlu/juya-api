## 最终契约编码核对与窄范围修复

父协调在最终产物核对中发现 canonical OpenAPI 导出受 Windows 默认编码影响。本轮实际读取确认：`project/juya-api/openapi/admin.json` UTF-8 解码在 offset42518、byte0xb0失败；`mini.json`在offset17883、byte0xcf失败；两者均可按GBK解码。原因是 `scripts/export-openapi.py` 的 `Path.write_text` 未显式指定编码；此前“导出命令exit0”并不能证明canonical为UTF-8。

已只修复工具链：`project/juya-api/scripts/export-openapi.py:21`固定 `encoding="utf-8", newline="\n"`。新增 `tests/test_openapi_export.py` 模拟GBK平台默认写入，使用包含中文的schema及隔离工厂，不连接数据库、不写真实契约；修复前重现UTF-8解码失败，修复后1 passed（0.55s）。重新执行原导出脚本，更新API canonical `openapi/{admin,mini}.json`；复制到各前端 `openapi/`，各自执行原 `pnpm generate:api`，更新 `src/shared/contracts/generated/{admin-api,mini-api}.d.ts`，未手改生成类型。
