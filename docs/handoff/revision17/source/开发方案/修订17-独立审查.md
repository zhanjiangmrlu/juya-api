# 修订17独立代码审查

审查日期：2026-10-28。审查对象为三个实际工作区的未提交修订17实现：`project/juya-api`、`project/juya-admin`、`project/juya-miniapp`，后端迁移至0022。以当前开发版需求及《修订17-实施与验收》为依据，结合审查diff、实际源文件及三端实施报告进行独立静态检查。

本次没有修改产品源码、运行清表测试、连接云接口、推送或部署。实施报告中的测试数字属于实施者证据，本次没有重复运行，也不将它们当作独立动态复现。以下问题均可由实际请求和控制流定位；未验证真机、微信真实认证、真实ASR词轴及全部53张画板。

## 结论

- **Spec compliance：需修复后再验收。** 独立听读模型、发布快照、两套顺序与M、共享授权和打卡、同版本进度、持久独立词轴任务等主要能力已有实现，但有图流程、未知结果恢复、未完成导入发现、最近学习统计和配置审计仍存在需求差距。
- **Code quality：需修复。** 后端统一`operate`、用户写锁、数据库唯一键、发布与草稿隔离、受控资源及任务输入hash的方向合理；主要缺陷集中在前端没有完整承接后端鉴权/幂等边界，以及部分跨模块派生状态遗漏。当前不建议宣称本轮完整验收通过。

## 必须处理的发现

### R1 — P1：小程序听读缩略图没有传递接口要求的登录凭证

- 位置：`project/juya-miniapp/src/features/listening/components/listening-article-card.vue:12-14,31`；`src/sub-packages/listening/article.vue:83`。契约依据：`project/juya-api/src/juya_api/listening_api.py:1159-1173`及`dependencies.py:57-64`；`project/juya-miniapp/src/services/platform.ts:19-22`。
- 触发：给有效发布文章配置图片，进入主题列表、收藏/已学列表或文章详情。
- 实际后果：`thumbnail_url`是要求`Depends(learner)`的地址，learner只从Authorization Bearer读取会话；前端`resourceURL`仅拼接API域名，随后直接赋给`<image src>`，没有认证下载或签发图片凭证。普通图片请求无法通过该接口鉴权，缩略图持续401，点击原位重试也只重发同一无凭证地址。真实联调的无图样本不能覆盖该缺陷。
- 最小修复：为安全派生缩略图提供会话绑定短期票据并让图片组件消费，或复用认证下载到临时文件的能力。必须保留“受限发布文章可读安全缩略图、原图仍需学习权限”的区别，不能简单取消原图鉴权。补一项有图真实HTTP/浏览器验证。
- 需求：37.3、T247—T249。

### R2 — P1：后台新建操作丢响应后会更换幂等键，可能生成重复对象

- 位置：`project/juya-admin/src/pages/listening/listening-edit-page.vue:87-98`；`src/features/listening/listening-settings.vue:144-165`；基础实现`src/services/http-client.ts:128-133`。
- 触发一：新建文章POST已提交，但返回丢失；表单仍没有article.id。管理员修改任一字段再保存，`pendingSave.snapshot !== snapshot.value`会丢弃旧闭包并创建新POST键，生成第二篇文章。
- 触发二：新增分类或主题POST已提交但返回丢失，直接点击原表单保存重试。`saveHierarchy`每次重新创建`listeningOperation`，即使输入完全相同也使用新键；服务端没有名称唯一约束，正常生成重复分类/主题。
- 当前入口已核实：`src/router/index.ts:12-14`的分类/主题独立路由加载`listening-catalog-page.vue`，该页渲染`ListeningSettings`并调用其实际表单`saveHierarchy`；不是未使用旧代码。
- 最小修复：将未知操作的key、冻结请求和对象身份保留到结果确认；先查询原操作回执，查无结果后仍以原key恢复原请求，禁止因改输入而直接换键重建。确认原创建成功后，后续编辑使用返回的id/revision。至少覆盖“成功响应丢失→改输入→重试”和“分类同输入重复点击”的测试。
- 需求：20章持久幂等与结果查询、36.5.2管理异常恢复；项目AGENTS“每个写操作…持久幂等”。

### R3 — P1：小程序重启后，查无回执的未知听读操作没有恢复出口

- 位置：`project/juya-miniapp/src/features/listening/listening-service.ts:32-36,44-50`；依赖`src/services/operation-service.ts:69-83,162-173`。
- 触发：完成、收藏或进度请求在到达服务端前断网，客户端保存pending元数据；关闭/重启小程序后再点击重试。pending元数据持久化，但冻结正文`fingerprints`仅在内存，重启后为空；服务端正确返回`operation_unknown`。
- 实际后果：听读包装器每次都先调用`operations.recover`，后者在`!frozen`时抛出，无法到达`operations.run`。听读界面没有`rebind`或“查询后重新确认原请求”的入口，pending也不会清除；因此该action（按文章区分）的后续完成、收藏或进度同步永久卡在同一未知记录，普通再次重试无效。
- 最小修复：消费既有操作服务的查无回执/重新确认能力，在校验当前账号和原版本后，由用户确认固定正文，以原key恢复；或者安全持久化足够的原请求数据。不可用清pending并换新key掩盖未知结果。测试需重建operation service实例，覆盖内存正文丢失而持久元数据仍在的情况。
- 需求：36.3.4进度失败可恢复、36.5.2未知完成先查询、T229—T230。

### R4 — P2：只保存部分候选会把整个导入批次标成已完成，使剩余资料失去恢复入口

- 位置：`project/juya-api/src/juya_api/listening_imports.py:938`；`project/juya-admin/src/pages/listening/listening-import-page.vue:285-288`。
- 触发：同批A、B两个可保存候选，仅选择A并成功保存。服务端只根据本次`results`是否失败设置整批`status='saved'`，没有检查未选中B仍未保存。
- 实际后果：离页后，“继续处理”列表排除saved批次，B虽然已持久暂存且可恢复，却没有入口重新找到。另一个同类边界是页面仅取最新50个全部批次再本地筛选；较早未完成批次也会被新完成批次挤出恢复集合。
- 最小修复：整批完成状态从全部未移除候选计算；仍有可处理候选时保留review/partial。恢复查询在服务端过滤真正未完成集合并提供分页，前端消费该集合。补“选择性保存后离页恢复”和“超过50批”的边界验证。
- 需求：38.3及17.8的真实可恢复未完成批次、T196、T252—T257。

### R5 — P2：听读完成没有更新后台“最近学习”统计

- 位置：`project/juya-api/src/juya_api/learning_service.py:80-84`；消费者`project/juya-admin/src/pages/users/user-list-page.vue:271`、`src/pages/users/user-detail-page.vue:114`。
- 触发：用户只完成听读，或完成场景之后又完成/复习了听读。
- 实际后果：统一统计已经返回听读完成数和共享打卡，但`last_studied_at`仍只查询场景`Completion.last_completed_at`；仅听读用户显示未开始，其他用户显示较旧的场景时间，A05/A06与真实学习行为不一致。
- 最小修复：最近学习取本人场景与听读成功完成时间的最大值；无记录继续为空。不要以阅读进度或打开时间代替完成时间。覆盖仅听读、两类先后及跨日复习。
- 需求：14章最近学习、36.3/36.5两类学习统计、需求行618的听读复习更新最近学习。

### R6 — P2：听读M和排序变更未持久记录前后结果

- 位置：`project/juya-api/src/juya_api/listening_service.py:534-554,575-591`；`src/juya_api/listening_api.py:429,486`；`src/juya_api/models.py:91-97`。
- 触发：管理员保存听读全局/主题排序，或修改M配置。
- 实际后果：现值与revision被覆盖，通用Audit只记录admin、action和time，听读调用甚至没有object_id；未保存排序作用域/主题、原顺序、新顺序、原M、新M及名单影响。后续无法按需求核查该次变更前后事实。加密Operation回执只保存本次结果，并不构成完整的before/after记录。
- 最小修复：在同一事务写专用历史或扩展审计结构，记录明确作用域/对象及before/after；复用已有AccessHistory风格可减少重复，但必须区分场景与听读。迁移只能增量，不改历史用户事实。
- 需求：36.4.1第6条明确“配置与排序变更记录管理员、时间及前后结果”。

### R7 — P2：“下一篇”继续压入详情页，返回无法恢复原列表来源

- 位置：`project/juya-miniapp/src/sub-packages/listening/article.vue:137`；`src/features/listening/listening-service.ts:68-71`；`src/features/listening/use-listening-article.ts:531-534`；`src/services/navigation.ts:107-108`。
- 触发：从主题列表/收藏/学习记录进入A，完成后点击下一篇B，再点击详情返回。
- 实际后果：下一篇复用了首入详情的`uni.navigateTo`，把B压在A上；`leave`最终`navigateBack()`只退一页，因此回到A而不是原主题/收藏/记录来源。连续下一篇持续增加详情栈，也没有导航失败处理，无法作为任意长度队列的稳定前进方式。
- 最小修复：区分首入与同队列推进，下一篇使用替换当前详情或同页切换，保留原来源与冻结queue_token；切换前保存进度并处理导航失败。原场景`detail.vue:820`已有使用redirectTo推进的实现可参考。
- 需求：2.2来源恢复、36.3.1同主题后续篇目与跨分页队列。
